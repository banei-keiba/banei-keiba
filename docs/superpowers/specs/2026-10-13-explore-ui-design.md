# Phase 3 探索 UI 設計

作成: 2026-10-13 ／ 対象: docs/architecture.md の Phase 3（探索 UI）

## 1. 目的

予想の材料を探す読者が、条件を組み合わせて勝率・連対率・複勝率・回収率を見られるページを作る。
公開サイト（https://banei-keiba.pages.dev/）の一部として出す。

**決定事項（ユーザー確認済み）**

| 項目 | 決定 |
|---|---|
| 対象読者 | 予想の材料を探す読者（公開サイトの 1 機能） |
| 方式 | 2 軸までのクロス表を、組み合わせごとに静的ページとして生成する（SSG・JS ゼロ） |
| 軸 | 馬場水分・天候・月・人気・重量差・馬番・馬齢・性別の 8 軸 |
| 更新 | 終わったシーズンまでを集計し、年 1 回だけ変わる |
| 範囲外 | 騎手・調教師（Phase 4 で決める）、クラス、3 軸以上 |

## 2. 計画（DuckDB-WASM）を採らない理由

architecture.md は「集計済み Parquet + ブラウザ内 DuckDB-WASM で自由にクロス集計」としていた。
実データ（2007〜2026-10、306,585 出走）で測ると成り立たない。
（§2・§3.1 の測定は試作時の定義: 着順のある出走・暦年。§4 の定義とは少し違うが結論は変わらない）

| 組み合わせ | 30 件未満のマスを消したときに残る出走（全期間 / 直近 3 年） |
|---|---|
| 1 軸 | 100% / 99.9% 以上 |
| 2 軸（45 通り） | 最悪 98.1% / 最悪 93.7%（騎手×調教師） |
| 3 軸（120 通り） | 最悪 71.1% / 最悪 5.5% |
| 全 10 軸 | **0% / 0%** |

- 全軸のキューブはすべてのマスが 30 件未満になる
- 軸を減らしても、細かいマスを消してから足し合わせると消えた分だけ件数が少なく出る
  （「人気 1 の勝率」が実際と違う値になる）。正しい値を出すには、**見せる組み合わせごとに
  事前集計するしかない**
- DuckDB-WASM 自体も数 MB あり、JS ゼロ・全 4 ページ 92KB の現状と合わない

## 3. 公開ポリシーとの両立

### 3.1 消すと引き算で割り出せる

小さいマスを消すだけでは、別に公開した合計との引き算で値が割り出せる。実測:

- 小さいマスを含む行 1,150 行のうち **289 行**で、消したマスが 1 つだけで、行の合計
  （1 軸の表）から値がそのまま分かる（例: 騎手×水分・直近 3 年で、ある騎手の 10 件のマス）
- 全期間と直近 3 年の両方に出るマス 4,055 個のうち **64 個**で差が 1〜29 件

### 3.2 版と版の差でも割り出せる

集計は日次で更新され、public リポジトリに毎日コミットとして残る。前日の版との差を取ると、
その日のレースだけの集計が出る。細かい表を毎日更新すると、複数の表の差を突き合わせて
その日の結果表がほぼ復元できる。**30 件ルールは各版だけでなく、版と版の差にも当てる。**

騎手・調教師を含めて年 1 回更新にすると、1 シーズンごとに 30 件以上が必要になり、
騎手の表の 53〜100% が「その他」になった（実測）。そのため人の軸は外した。

### 3.3 規則

1. **各表は対象の出走をもれなく分ける。マスを消さない。** 規則を満たさない区分は隣とまとめる
2. **期間帯ごとに、すべてのマスが 0 件か 30 件以上**。期間帯は次の単位:
   - 2007〜2022 シーズンはひとかたまり
   - 2023 シーズン以降は 1 シーズンずつ

   版の差で切り出されるのはこの単位だけ。初回公開（2025 シーズンまで）の「全期間 − 直近 3
   シーズン」が 2007〜2022 のかたまりで、以後は年 1 回の更新ごとに 1 シーズンずつ切り出される。
   基準の 2023 は**初回公開の直近 3 シーズンの始まりで、後から変えてはいけない**
   （変えると切り出される単位が変わる）。定数 `FIRST_RECENT_SEASON = 2023` として置く
3. 区分のまとめ方は表ごとに 1 つに固定し、期間（全期間 / 直近 3 シーズン）で変えない。
   まとめるのは区分（行・列）単位で、マス単位ではない

### 3.4 シーズンと締め

- シーズンは 4/1〜翌 3/31。開始年で呼ぶ（2025 シーズン = 2025-04-01〜2026-03-31）
- **締めは 5/1**。JST の今日が Y 年 5/1 以降なら `through_season = Y - 1`、それより前なら `Y - 2`
  - 2026-10-13 → 2025 シーズンまで / 2026-04-20 → 2024 シーズンまで
  - 3/31 ではなく 5/1 にするのは、日次収集が直近 30 日を取り直すため。取りこぼし
    （2026-08-17 の例）があっても 1 か月で埋まる。4/1 に締めると、埋まった 1 日ぶんの差が公開される
  - 日付は JST で明示的に判定する（ランナーは UTC。`ingest/results.py` の `JST` と同じ扱い）
- 期間は「全期間」（2007〜through_season）と「直近 3 シーズン」（through_season-2〜through_season）
- `through_season - 2 < FIRST_RECENT_SEASON` になる設定は誤りなので実行時に止める

## 4. 集計の定義

### 4.1 対象の出走

- `results` のうち `status` が `取消`・`除外` 以外。**中止（1,274）・失格（643）は含める**
  （人気が付いていて馬券は外れ扱い。回収率の分母に入る）
- `race_date` が 2007 シーズン〜through_season の範囲
- 複勝の払戻が 1 件も無いレース（2026-03 までで 7 レース・27 出走、3〜4 頭立て）は除く。
  複勝の指標が定義できないため
- 2025 シーズンまでで 299,447 出走

### 4.2 軸と基本区分

軸ごとに並び順を決め、まとめるときは隣とだけまとめる。

| 軸 | キー / URL | 基本区分 | 定義 |
|---|---|---|---|
| 人気 | `popularity` | 1〜10 | `results.popularity` |
| 馬番 | `post` | 1〜10 | `results.horse_no` |
| 重量差 | `weight_diff` | 0 / 1〜10 / 11〜20 / 21〜30 / 31kg〜 | レース内の出走馬（取消・除外を除く）で最も軽い積載重量との差 |
| 馬齢 | `age` | 2〜9 / 10 歳〜 | `results.age` |
| 性別 | `sex` | 牝 / 牡 / セン | この並び（セン を 牡 の隣に置く） |
| 馬場水分 | `moisture` | 〜0.9 / 1.0〜1.4 / 1.5〜1.9 / 2.0〜2.4 / 2.5〜2.9 / 3.0〜 | `races.moisture` |
| 天候 | `weather` | 晴 / 曇 / 雨・雪 | 雨・雪 = 小雨・雨・小雪・雪。この並び |
| 月 | `month` | 4 月〜翌 3 月 | シーズン順。3 月と 4 月は隣ではない |

- 馬番のキーを `horse_no` にしないのは、`aggregates.FORBIDDEN_KEYS` に当たるため
  （生データの個体キーと同じ名前を集計に使わない）
- URL 上の軸の順番は上の表の順で固定し、同じ組み合わせが 2 つの URL にならないようにする
- まとめた区分の表示名は「先頭の下限〜末尾の上限」（例: `9〜10`、`2.5〜`、`4〜5月`）

### 4.3 区分のまとめ方

表（1 軸または 2 軸）ごとに次を繰り返す。決定的に動くこと（同じ入力なら同じ出力）。

1. 基本区分から始め、期間帯ごとに各マスの出走数を数える
2. どの期間帯にも 0 < n < 30 のマスが無ければ終わり
3. 違反マスのうち n が最小のものを選ぶ（同値なら期間帯の古い順 → 軸の順 → 区分の順）
4. その違反の期間帯で、違反マスが属する各軸の区分の出走数を比べ、少ない軸を選ぶ
   （同値なら表の軸の順で先の軸）。区分が 1 つしか残っていない軸は選ばない
5. その区分を、同じ期間帯で出走の少ない隣の区分とまとめる（同値なら前の区分）
6. 1 に戻る

試作（使い捨て）で測った結果:

- 1 軸の 8 表はすべて基本区分のまま
- 2 軸の 28 表のうち 23 表で一部がまとまる。最も粗くなるのは 水分×月（水分 4 区分）、
  重量差×性別（重量差 3 区分）、馬齢×性別（馬齢 6 区分）
- 性別は多くの表で「牡〜セン」になる（近年は セン が少ない）

実装後、`banei export` の結果がこの測定と一致することを確かめる。

### 4.4 指標

各マスに次を持つ。率はすべて % で小数 1 桁に丸める。

| キー | 指標 | 定義 |
|---|---|---|
| `n` | 出走数 | 取消・除外を除く |
| `win_rate` | 勝率 | 1 着の割合。同着は 1 着として数える |
| `top2_rate` | 連対率 | 2 着以内の割合 |
| `place_rate` | 複勝率 | 複勝の払戻対象になった割合。7 頭以下は 2 着まで、8 頭以上は 3 着までなので 3 着内率とは別物 |
| `win_roi` | 単勝回収率 | 単勝払戻の合計 ÷ (n × 100) |
| `place_roi` | 複勝回収率 | 複勝払戻の合計 ÷ (n × 100) |

払戻は `payouts` の該当券種を馬番で結合して得る（同着の分割払戻もそのまま入る）。

## 5. 出力（export → JSON）

- 新規モジュール `src/banei/export/explore.py`。既存の `export.build()` に組み込み、
  違反があれば既存の集計も含めて書き出し全体を止める
- 出力先 `web/src/data/explore/`。1 軸 8 ファイル（`popularity.json`）、2 軸 28 ファイル
  （`popularity__moisture.json`）。両期間を 1 ファイルに入れる
- **生成時刻を入れない**（入れると毎日内容が変わり、検査 3 が成り立たない）

形（値は例）:

```json
{
  "axes": ["popularity", "moisture"],
  "through_season": 2025,
  "bins": {"popularity": ["1", "2", "…"], "moisture": ["〜0.9", "…", "2.5〜"]},
  "periods": {
    "all": {
      "first_season": 2007, "last_season": 2025,
      "total": {"n": 299447, "win_rate": 10.0, "…": "…"},
      "margins": {"popularity": [{"popularity": "1", "n": 29950, "…": "…"}],
                  "moisture": [{"moisture": "〜0.9", "n": 25000, "…": "…"}]},
      "cells": [{"popularity": "1", "moisture": "〜0.9", "n": 2301, "win_rate": 36.1, "…": "…"}]
    },
    "recent3": {"first_season": 2023, "last_season": 2025, "…": "…"}
  }
}
```

- `margins`（全体の行と列）と `total` は、まとめた区分でのマスの合計。新たな数字は出ない
- 0 件のマスは `cells` に入れない（画面では「—」）
- 1 軸のファイルは `cells` と `total` を持つ（`margins` なし）
- `cells`・`margins`・`total` は既存の `policy_violations()` も通す（個体キーなし・n ≥ 30）

## 6. 実行時検査（違反で PolicyError）

1. すべてのマスが、どの期間帯でも 0 件か 30 件以上
2. 各期間で、マスの n の合計が対象の出走数と一致する（もれなく分けている）
3. 書き出し先にある前回の出力と比べ、`through_season` が同じなのに内容が違えば止める
   - 前回の出力が無い（初回）場合、`through_season` が進んだ場合は通す
   - 締めたシーズンのデータが後から変わった（修正・補完）ことを意味する。その差は小さな
     集計の漏れになるので、人が判断するまで公開しない。対応手順は CLAUDE.md に書く

日次ワークフローは `git add web/src/data` をそのまま使えるので変更しない。

## 7. ページ（Astro）

| ページ | URL | 数 |
|---|---|---|
| 入口 | `/explore/` | 1 |
| 1 軸 | `/explore/<軸>/<期間>/`（例 `/explore/popularity/all/`） | 16 |
| 2 軸 | `/explore/<軸>/<軸>/<期間>/`（例 `/explore/popularity/moisture/recent3/`） | 56 |

期間のスラッグは `all` / `recent3`。全 73 ページ。2 軸ページは HTML 約 30KB（圧縮前）の見込み。

**2 軸ページ**

- 見出しに 軸 × 軸、期間（シーズン範囲と出走数）
- 「もう一方の軸」「期間」「1 軸だけで見る」の切り替えはリンク
- 指標の切り替えはラジオボタン + CSS のタブ（JS なし。キーボードで操作できる）
- 表は区分の多い軸を行にする。各マスに率と出走数。端に「全体」の行と列
- マスに値の濃淡を付ける。色は `--data` の単色の濃淡で、マス内の文字のコントラストは
  global.css の系列色と同じ検証スクリプトで確かめる（目視で決めない）
- 出走数 100 未満のマスは文字を薄くし、「率の振れが大きい」と注記する
- 表の下に注記: 回収率は 1 回の高配当で大きく動く / 多数のマスを見比べれば偶然でも 100% を
  超えるマスはいくつか出る

**1 軸ページ**: 1 つの表に出走数と 5 指標を列として並べる（タブなし）。下にその軸を含む
2 軸ページへのリンク。

**入口ページ**: 何を数えているか、終わったシーズンまでで年 1 回更新すること、区分を
まとめることとその理由（公開方針）、上の注記。1 軸 8 表と 2 軸 28 組へのリンク。

ヘッダーのナビに「探索」を足す。

## 8. テスト

pytest・合成データ（実ページ・実データは使わない）。新規 `tests/test_explore.py`。

- 区分のまとめ方
  - 違反が無ければ区分を変えない
  - 隣とだけまとめる。違反した期間帯で少ない側をまとめる
  - 乱数で作った表（シード固定で多数）で、まとめた後に「全マスが期間帯ごとに 0 か 30 以上」
    「合計が変わらない」が常に成り立つ
- 集計の定義
  - 取消・除外は除き、中止・失格は含む
  - 同着の勝ち馬は 2 頭とも 1 着として数える
  - 7 頭以下の複勝は払戻データどおりに数える
  - 複勝の払戻が無いレースは除く
  - 締め: JST 4/30 と 5/1 で `through_season` が変わる。UTC で前日になる時刻でも JST で判定する
- 実行時検査 1〜3 は、それぞれわざと違反を作ると PolicyError で止まり、何も書き出さない
- 書いたテストが違反を捕まえることは、検査コードをわざと壊して確かめる（validate と同じ要領）

**手元での確認**

- 実データで `banei export` を回し、区分の結果が 4.3 の測定と一致すること
- `npm run build` が通り、73 ページが生成され、サイズが見込みどおりであること
- 濃淡の色のコントラスト検証

## 10. 範囲外・後で決めること

- 騎手・調教師の切り口: Phase 4（騎手・馬ページ）が同じ問題を抱える。馬は通算 30 走未満も
  多く、さらに厳しい。Phase 4 の設計でまとめて決める
- クラス: レース名から単純な規則で取り出せるのは 87.6%。残りは昔の賞金額ベースのクラス名
  （「120万円未満」など）で、制度が途中で変わっている。対応づけに競馬の知識に基づく判断が要る
- 3 軸以上
- **今の公開ページにある差分の漏れ**: 人気別の表などは 1 行 3 万件台で 0.1% 単位に丸めて
  いるため、1 出走ぶんの変化は読めない。ただし件数の少ない行（`weight_handicap` の重量差
  80kg・n=31 など）は、1 出走増えたときに勝ったかどうかが分かる。`moisture_vs_time` の
  `fastest_sec` は 1 レースの値そのもの。architecture.md に既知の課題として記録し、別に直す
