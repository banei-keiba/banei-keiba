# Phase 4 騎手・調教師ページ設計

作成: 2026-10-14 ／ 対象: docs/architecture.md の Phase 4（馬・騎手ページ / SEO）のうち騎手・調教師ページ

## 1. 目的

騎手・調教師の名前で検索して来る読者と、予想の材料を探す読者に、1 人 1 ページの成績と
派生指標（人気から見込まれる勝ち数との差など）を見せる。公開サイト
（https://banei-keiba.pages.dev/）の一部として出す。

**決定事項（ユーザー確認済み）**

| 項目 | 決定 |
|---|---|
| 範囲 | 騎手・調教師のページ。馬ページと SEO まわり（sitemap・構造化データ）は別に設計する（§11） |
| 中身 | シーズンごとの成績と派生指標だけ。条件（人気・馬場水分など）で分けた表は載せない |
| 単位 | 1 人 × 1 シーズン（2007 シーズンから）。30 件未満の人・シーズンは「その他」にまとめる |
| 名前 | 略称 → 正式名の対応表をリポジトリに置き、騎手と調教師を 1 人 1 ページにまとめる。確かめられない人は略称のまま |
| URL | DB の略称から作る（`/people/鈴木恵/`）。対応表を直しても変わらない |
| 更新 | 締めたシーズンまで。探索 UI と同じく 5/1 の締めのときだけ変わる（年 1 回） |
| 方式 | export に専用の `people.py` を足す（探索 UI の軸として載せる案は採らない。§3.5） |

## 2. 前提の測定

実データ（2025 シーズンまで、探索 UI と同じ対象出走 299,447 件。§4.1）で測った。
（§2.1 と §2.3 は試作時の定義「着順のある出走」で測った。§4.1 の定義とは少し違うが結論は変わらない）

### 2.1 馬ページは今のルールではほぼ作れない

| | 値 |
|---|---|
| 2025 シーズンに走った馬 | 839 頭。シーズンの出走は中央値 20・最多 27。**30 回以上は 0 頭** |
| 2007〜2022 に 30 回以上走った馬 | 2,136 頭（多くは引退馬） |

版の差の規則（シーズンごとに 0 か 30 以上）の下では、どの馬も 2023 シーズン以降の成績を
出せない。日次で更新すれば前日との差が「その馬の昨日の着順」そのものになり、年 1 回でも
差は「その馬の 1 シーズンの成績」（30 件未満）になる。馬名検索の読者が探すのは現役馬なので、
狙っていた SEO にもほとんど効かない。馬ページの方針は別に決める（§11）。

### 2.2 騎手・調教師はシーズンの合計なら規則を満たす

| | 騎手 | 調教師 |
|---|---|---|
| 人数（2025 シーズンまで） | 51 | 45 |
| 2025 シーズンに出走あり | 26 | 26 |
| 1 シーズンの出走（中央値） | 約 640 | 約 460 |
| 人 × シーズン | 486 | 589 |
| うち 1〜29 件 | 7（すべて 2020 以前） | 4（すべて 2020 以前） |

### 2.3 条件で分けた表はほとんどの人で成り立たない

全員で同じ区分を使うと、人気でも馬番でも区分が 1 つにまとまる（騎乗の少ない騎手が 1 人いると
全体が粗くなる）。規則を満たす人にだけ表を出す方式だと、2025 シーズンに乗った 26 人のうち:

| 区分 | 騎手 | 調教師 |
|---|---|---|
| 人気 10 区分 | 10 | 10 |
| 人気 1 / 2〜3 / 4〜10 | 16 | 22 |
| 馬場水分 3% 未満 / 以上 | 3 | 1 |

馬場水分が残らないのは、最近のシーズンは水分の高いレースが少ないため（2025 シーズンは
4% 以上が 8 レース）。さらに、表を出す人と「その他」の顔ぶれが年ごとに入れ替わると、締めた
シーズンの内容が変わる。人ごとに区分をまとめる方式は、探索 UI の表との引き算（全員の表を
足すと探索 UI の表になる）を防ぐ検査を新しく作る必要がある。いずれも重いので、条件で分けた
表は載せない。騎手 × 馬（相性）は、全期間帯で 0 か 30 以上の組が 31,513 組中 5.7% しかない。

### 2.4 DB の名前は 3 文字の略称

`results.jockey` / `results.trainer` は結果ページの表記のまま（「鈴木恵」「竹ケ茉」、
全角スペースで 3 文字に詰めた「林　豊」）。騎手・調教師の ID やリンクは取り込んでいない。
騎手から調教師に移った人が 2025 シーズンまでで 6 人（西弘美・松田道・大河和・坂本東・千葉均・
山本正。いずれも略称は両方の役割で同じ文字列）、2026 シーズンにさらに 2 人（藤野俊・藤本匠）いる。

## 3. 公開ポリシーとの両立

### 3.1 2007 シーズンから 1 シーズンずつ載せてよい理由

探索 UI が 2007〜2022 を 1 つの期間帯にまとめているのは、「直近 3 シーズン」の枠が毎年ずれ、
版の差で 2023 以降が 1 シーズンずつ切り出されるため（FIRST_RECENT_SEASON）。人のページは
最初の版で 2025 シーズンまでを一度に出し、以後は締めが進むたびに新しいシーズンが 1 つ加わる
だけなので、2025 シーズン以前が版の差で切り出されることはない。そのため各シーズンの欄が
30 件以上という普通の規則で足りる。版の差で切り出されるのは新しいシーズンの欄（と、それを
足した通算）で、これも 30 件以上になる。

### 3.2 「その他」にまとめ、消さない

ある人・シーズンの欄だけを消すと、そのシーズンの合計（探索 UI の版の差などから分かる）から
他の人の欄を引いて値が割り出せる。そのため消さずに「その他（n 人）」にまとめ、「その他」も
0 か 30 以上にする（§4.3）。

### 3.3 通算は個人の欄に載せたシーズンだけの合計

「その他」にまとめたシーズンを通算に含めると、通算から個人の欄を引いて、まとめた値が出る。
通算は個人の欄に載せたシーズンの合計とし、画面にもそう注記する。

### 3.4 人気に関わる値は 2 つに絞る

平均人気と見込み勝ち数は、どちらも「その人がそのシーズンに何番人気に何回出走したか」（10 個の値。
1 回しか無い人気もある）の重み付き合計になる。この種の値を増やすと、連立方程式で人気別の内訳が
割り出せるようになっていく。出走数とあわせて式は 3 本で、10 個の値に対して足りない。新しい
派生指標を足すときは、この本数を増やさないこと。

### 3.5 探索 UI の軸として載せない理由

探索 UI の区分は表ごとに決まり、版をまたいで粗くなる方向にしか変えられない。騎手を軸にすると、
一度「その他」にまとめた騎手は以後ずっと個人として出せない（2 月にデビューした新人は永久に
ページを持てない）。人のページは「その他」へのまとめをシーズンごとに独立して決める。締めた
シーズンの顔ぶれはデータが変わらない限り変わらないので、版の差の問題も起きない。

## 4. 集計の定義

### 4.1 対象の出走

探索 UI と同じ（`explore._STARTERS` を import して共有する。定義が 2 か所に分かれると数字が
食い違う）。取消・除外を除き、中止・失格は含める。複勝の払戻が無いレースは除く。シーズンは
4/1〜翌 3/31、締めは 5/1（`explore.through_season`）。2025 シーズンまでで 299,447 出走。

### 4.2 単位

役割（`jockey` / `trainer`）× DB の略称 × シーズン。騎手の「藤野俊」と調教師の「藤野俊」は
別の行として集計・検査し、1 ページにまとめるのは表示のとき（§7）。

### 4.3 「その他」へのまとめ方

役割・シーズンごとに独立に決める。

1. そのシーズンの出走が 1〜29 件の人を「その他」に入れる
2. 「その他」が 1〜29 件なら、残りのうち出走数が最も少ない人（同数なら略称の順）を移し、
   30 件以上になるまで繰り返す

実データ（2025 シーズンまで）での結果:

| 役割 | 「その他」に入る人・シーズン | うち 2 で移された人 |
|---|---|---|
| 騎手 | 11（2008・2009・2010・2012・2019） | 4（2008 林義直 30 / 2009 貝羽智 86 / 2012 井上真 30 / 2019 竹ケ茉 169） |
| 調教師 | 8（2008・2018・2019・2020） | 4（2008 前原陽 188 / 2018〜2020 森芳浩 138・152・171） |

個人の欄が 1 つも無い人はいない。

「その他」は空でなければ必ず 2 人以上になる（1 人目は 1〜29 件なので、30 件以上にするには
もう 1 人が要る）。人数（`people_count`）と顔ぶれ（各人の `pooled_seasons`）は公開するが、
合計しか出ないので一人ひとりの値は割り出せない。

### 4.4 指標

各欄（人・シーズン、通算、「その他」、シーズン全体）に次を持つ。率は % で小数 1 桁に丸める。

| キー | 指標 | 定義 |
|---|---|---|
| `n` | 出走数 | 騎手は騎乗数、調教師は管理馬の延べ出走数 |
| `win_rate` / `top2_rate` / `place_rate` | 勝率・連対率・複勝率 | 探索 UI と同じ（`explore._metrics`） |
| `win_roi` / `place_roi` | 単勝・複勝回収率 | 探索 UI と同じ |
| `wins` | 勝ち数 | 1 着の数（一覧の順位に使う。勝率 × 出走数でほぼ分かる値なので新しい情報は出ない） |
| `avg_popularity` | 平均人気 | 人気の平均。小数 2 桁 |
| `expected_wins` | 見込み勝ち数 | 出走ごとに「そのシーズン全体のその人気の勝率」を足し上げたもの。小数 1 桁 |
| `wins_over_expected` | 見込みとの差 | 実際の勝ち数 − 見込み勝ち数。小数 1 桁 |

- 見込みに使う人気別の勝率は、そのシーズンの対象出走全体から計算する（10 個。公開しない内部の重み）。
  同着は 2 頭とも 1 着として数える（勝率の定義と同じ）
- 人気が 1〜10 以外の出走（2025 シーズンまでは 0 件）があれば、黙って除かずに止める（§6 の 2）
- 通算の見込み勝ち数は、載せたシーズンの見込み勝ち数の合計

## 5. 出力（export → JSON）

- 新規モジュール `src/banei/export/people.py`。`export.build()` から探索 UI と同じように呼び、
  違反があれば書き出し全体を止める
- 出力は `web/src/data/people.json` の 1 ファイル（約 90 人 × 最大 19 シーズンで数百 KB）。
  締めの検査を 1 回の比較で済ませるため、人ごとに分けない
- 生成時刻を入れない（探索 UI と同じ理由）

形（値は例）:

```json
{
  "through_season": 2025,
  "roles": {
    "jockey": {
      "seasons": [
        {"season": 2025, "total": {"n": 15210, "win_rate": 10.0, "…": "…"},
         "other": null}
      ],
      "people": [
        {"key": "鈴木恵",
         "seasons": [{"season": 2025, "n": 812, "win_rate": 14.2, "…": "…"}],
         "pooled_seasons": [],
         "career": {"first_season": 2007, "last_season": 2025, "n": 15000, "…": "…"}}
      ]
    },
    "trainer": {"seasons": [], "people": []}
  },
  "pages": [
    {"slug": "鈴木恵", "name": "鈴木恵介", "name_confirmed": true,
     "jockey": "鈴木恵", "trainer": null, "active": true}
  ]
}
```

- `other` は「その他」の欄（`people_count` に人数）。そのシーズンに無ければ `null`
- `roles` が集計、`pages` が表示（対応表から作る）。§6 の検査 3 は `roles` だけを比べる
- **キー名の注意**: `policy_violations()` は `n` と `n_` で始まる整数を件数列とみなして 30 以上を
  求めるので、人数は `n_people` ではなく `people_count` にする。`status` は個体特定キーとして禁止
  されているので、現役かどうかは `active` にする
- 締めたシーズンの出走が 1 件も無いときは出力を作らない（テスト用の小さな DB など。探索 UI と同じ）

## 6. 実行時検査（違反で PolicyError）

1. `roles` の全行（個人の欄・通算・「その他」・シーズン全体）が `policy_violations()` を通る
   （個体特定キーなし・n ≥ 30）
2. 役割・シーズンごとに、個人の欄の n と「その他」の n の合計が、そのシーズンの対象出走数と一致する。
   人気が 1〜10 以外の出走があれば止める
3. 書き出し先にある前回の `people.json` と比べ、締めたシーズンの `roles` が変わっていれば止める。
   締めが同じなら `roles` が同じこと。締めが進んだときは、今の DB から前回の締めで作り直して前回と
   比べる。締めが戻っている・前回の出力が読めない場合も止める（探索 UI の検査 3 と同じ）
4. 対応表の検査: 同じ略称が二重に登録されている、URL が重複する、表が読めない場合は止める

表に無い略称は止めずに警告する（§7）。

**止まったときの対応**: CLAUDE.md の「締めたシーズン（… まで）の内容が変わった」の手順に
人のページを含める。人のページでは、変わった人・シーズンの出走数の差がすべて 0 か 30 以上なら
公開してよい。

## 7. 正式名の対応表

`src/banei/export/people.toml`（標準の `tomllib` で読む）。

```toml
[[person]]
name = "鈴木恵介"        # 正式名
jockey = "鈴木恵"        # DB の騎手の略称（騎手でなければ書かない）
trainer = "…"            # DB の調教師の略称（調教師でなければ書かない）
source = "https://… (2026-10-14 確認)"
```

- 騎手と調教師を兼ねた（移った）人は 1 行にまとめ、1 ページにする
- **URL（`slug`）は DB の略称から空白を除いたもの**。兼ねた人は騎手の略称を使う。正式名が後から
  分かっても URL は変わらない（検索エンジンの評価とリンクを保つ）
- 正式名を確かめられない人は表に書かない。ページは略称のまま（`name_confirmed: false`）。推測で埋めない
- 表に無い略称（新人など）は略称のままページを作り、「対応表に無い略称」を警告する。正式名は後から
  足せばよく、表示が変わるだけで集計も URL も変わらない
- 表は公式の騎手・調教師の紹介ページ（ばんえい十勝の公式サイト、地方競馬全国協会の名鑑）で 1 人ずつ
  確かめ、出典と確認日を書く。実装時に作り、ユーザーが確認してからコミットする

**できないこと**: 同じ略称の別人（親子など）は DB 上で区別できず、成績は合算されたままになる。
対応表で分けられるのは表示だけ。今のデータでは例が見つかっていない。

## 8. ページ（Astro）

| ページ | URL | 数 |
|---|---|---|
| 一覧 | `/people/` | 1 |
| 1 人 | `/people/<slug>/`（例 `/people/鈴木恵/`） | 約 90（騎手 51 + 調教師 45 − 兼任 6。対応表で確定） |

全ページ SSG・JS ゼロ。noindex はサイト全体と同じく独自ドメインが決まるまで付けたまま。

**一覧**

- 最新の締めたシーズンの順位表（騎手・調教師それぞれ、勝利数順）。勝率・回収率・見込みとの差を
  並べ、「その他（n 人）」の行も入れる（もれなく分けた表として見せる）
- 全員の一覧。現役（最新の締めたシーズンに出走あり）と過去の人に分けて各ページへリンク
- ヘッダーのナビに「騎手・調教師」を足す

**1 人のページ**

- 題「鈴木恵介 騎手の成績」（対応表に無い人は略称）。兼ねた人は「騎手・調教師」
- 冒頭に最新の締めたシーズンの要点（出走数・勝率・見込みとの差）。そのシーズンに個人の欄が無ければ
  個人の欄がある最後のシーズン
- シーズン別の表（`DataTable`）。「その他」にまとめたシーズンは「—（その他にまとめたため非表示）」の
  行として残し、通算はその行を除いた合計だと注記する。30 件以上でも §4.3 の 2 で移された人がいるので、
  「30 件未満」とは書かない
- 図は 1 つ: シーズンごとの「実際の勝ち数 − 見込み勝ち数」の折れ線。系列が 1 本なので凡例なし、値は
  両端だけ直接ラベル。0 の参照線のため `LineChart` に `refValue` を足す（`ColumnChart` は負の値を
  描けない）。参照線のラベルは置かず副題で説明する（最後の点が 0 に近いと端点のラベルと重なる）。
  x 軸がシーズン（2025）なので、`toLocaleString` で「2,025」にならないよう `xFormat` も足す。
  個人の欄が 2 シーズン以上ある人だけに出す。表ビューを付ける
- 役割が 2 つある人は、役割ごとに表と図を並べる
- 注記: 集計の期間、年 1 回 5/1 に更新すること、通算の定義、データ方針へのリンク
- 配色は `global.css` のトークン（CLAUDE.md「図版を足すときの決まり」）

## 9. テスト

pytest・合成データ（実ページ・実データは使わない）。新規 `tests/test_people.py`
（`tests/test_explore.py` の合成 DB の作り方に合わせる）。

- 集計: 小さな合成シーズンで各指標が手計算と一致する（勝率・連対率・複勝率・回収率・平均人気・
  見込み勝ち数・見込みとの差）。同着、中止を含めること、取消・除外を除くこと
- 「その他」: 1〜29 件の人・シーズンが入る / 「その他」が 30 件未満なら出走数の最も少ない人が移る
  （同数なら略称の順）/ 通算に「その他」のシーズンが入らない / シーズンごとに独立に決まる
- 検査: まとめる処理をわざと壊すと検査 1 で止まる / 対象出走のもれや想定外の人気で検査 2 で止まる /
  締めたシーズンに 1 レース補完すると検査 3 で止まる / 同じデータなら毎日回しても締めが進んでも通る /
  前回の出力が読めない・締めが戻ると止まる
- 対応表: 表に無い略称は警告だけでページが作られる / 二重登録・URL の重複で止まる / 表の名前を
  直しても検査 3 に引っかからない / 兼ねた人が 1 ページになる
- 公開ポリシー: `people.json` の全行が `policy_violations()` を通る。export に組み込まれ、違反があれば
  書き出し全体が止まる
- 書いたテストが違反を捕まえることは、検査コードをわざと壊して確かめる
